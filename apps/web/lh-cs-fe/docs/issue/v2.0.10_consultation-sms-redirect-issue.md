# 상담실 생성 직후 SMS 인증 페이지로 이동하는 현상 정리

## 현상
- 상담실 생성 버튼 클릭 후 `/consultations` API 호출 시점에 인증이 끊기면서 앱이 `/login`으로 강제 이동하고, 이어서 `/verify-sms`로 자동 리다이렉트되며 `POST /auth/login/send-code`(2차 인증 발송)가 호출된다.
- 네트워크 탭에는 직전 `GET /users/profile`가 304(Not Modified)로 보이지만, 이는 원인이 아니라 로그인 페이지에서 실행된 캐시 재검증 결과다.

## 원인 흐름
1. `POST /consultations` 호출 중 액세스 토큰 만료·CSRF 오류 등으로 401/403이 발생.
2. 전역 Axios 인터셉터(`src/shared/api/api-client.ts`)가 토큰 리프레시를 시도하고 실패 시 `redirectToLogin()`을 통해 `/login`으로 이동.
3. `/login`에서 `AuthInitializer`가 리프레시 토큰으로 재인증을 시도하고, `useProfile`이 실행돼 304가 찍힌다.
4. 로그인 페이지의 `useEffect`가 “인증 상태이면 무조건 `/verify-sms`로 보내라”는 로직을 수행(`src/pages/login/ui/login-page.tsx`), 결과적으로 `VerifySmsPage` 진입 시 `sendLoginCode`가 자동 호출된다.

## 재현 조건(추정)
- 상담실 생성 API 호출 시점에 액세스 토큰이 만료됐거나, 메모리 저장소(`tokenStorage`) 특성상 페이지 리로드로 토큰이 사라진 상태에서 API를 호출했을 때.
- CSRF 토큰 검증 실패로 403이 발생한 경우에도 동일 흐름 가능.

## 대응 방안 제안
1. **리다이렉트 원인 로깅**: `api-client` 401/403 분기에서 `originalRequest.url`, `status`, `token 존재 여부`를 `console.error`가 아닌 Toast/로그 수집으로 남겨 원인(만료 vs CSRF)을 명시적으로 파악.
2. **로그인 페이지 가드 완화**: `/login`에서 인증된 경우라도 `location.state.from`이 `/login` 자체이거나 직전 경로가 이미 보호된 페이지였다면 즉시 `/verify-sms`로 보내지 말고 원래 경로로 복귀하도록 조건 분기 추가.
3. **토큰 보존/리프레시 안정화**: 메모리 토큰 소실이 잦다면 액세스 토큰을 세션 스토리지 등 휘발성 스토리지에 저장하거나, `AuthInitializer`에서 리프레시 실패 시 바로 `/verify-sms`로 보내지 않도록 하여 불필요한 2차 인증 발송을 막는다.
4. **UX 보호**: `/verify-sms` 진입 시 `location.state`에 로그인 비밀번호·리다이렉트 정보가 없으면 “세션 만료” 메시지 후 `/login`으로만 돌려보내 `sendLoginCode` 호출을 막는다.

## 즉시 후속 작업
- 위 1번(로그 보강)과 2번(가드 조건 완화)을 우선 적용해 재발 지점을 캡처하고, 필요 시 3·4번을 추가 반영한다.

## 추가 제안: 액세스 토큰 세션 스토리지 보완 설계
- 기본 저장소는 현재처럼 메모리(`tokenStorage`)를 유지하되, “새로고침 복구용”으로 세션 스토리지에 만료 시각과 함께 보관하는 얇은 래퍼를 둔다.
- 페이지 초기화 시 세션 스토리지에 유효한 토큰이 있으면 `tokenStorage.setTokens`로 복구하고, 만료됐거나 파싱 실패 시 바로 삭제한다.
- 구현 가이드(요약):
  1. `tokenStorage`에 세션 스토리지 읽기/쓰기 래퍼 추가: `{ accessToken, expiresAt }`를 JSON으로 저장. 저장 시 만료 시간을 명시적으로 함께 넣는다.
  2. `AuthInitializer`에서 메모리 토큰이 없으면 세션 스토리지를 조회해 유효 토큰이면 `setTokens`로 복원하고, 아니면 삭제.
  3. 리프레시/로그인 성공 시에도 세션 스토리지 값을 갱신하고, 로그아웃/리프레시 실패 시 세션 스토리지도 함께 비운다.
- 보안 주의: 세션 스토리지는 JS 접근 가능하므로 XSS 방어(CSP, 입력 검증, 라이브러리 업데이트)를 병행해 탈취 면적을 최소화한다.
